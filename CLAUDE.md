# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Расширение Chrome (Manifest V3), которое рисует копию встроенной панели закладок
внутри страницы, но в несколько строк. Сборка не требуется — исходники и есть то,
что грузится в браузер.

## Команды

```powershell
pwsh -File build.ps1        # dist\dbb-<version>.zip + печатает состав архива
```

`build.ps1` копирует только белый список путей (`manifest.json`, `_locales`,
`background`, `content`, `icons`, `newtab`, `options`, `popup`). Всё остальное —
README, `store/`, docs — в пакет не попадает. При добавлении новой папки с кодом
её нужно внести в `$include`, иначе она молча не уедет в магазин.

Тестового фреймворка и линтера нет. Синтаксис проверяется так (файлы — смесь ESM
и классических скриптов, поэтому копия с расширением `.mjs`):

```bash
cp content/content.js /tmp/c.mjs && node --check /tmp/c.mjs
```

Функциональная проверка — только вживую в браузере, см. «Отладка в Chrome».

## Архитектура

### Три контекста и почему между ними прокси

`chrome.bookmarks` недоступен контент-скрипту. Поэтому **все** операции с
закладками идут через service worker, который принимает только белый список
методов (`BOOKMARK_METHODS` в `background/service-worker.js`). Страница не может
через расширение сделать с закладками больше, чем делает сама панель. Добавляя
новую операцию, расширяйте этот список осознанно.

Протокол — один `chrome.runtime.onMessage` с таблицей `HANDLERS`:
`bookmarks` (прокси), `open` / `openAll`, `clipSet` / `clipGet` / `clipPaste`
(буфер вырезать-копировать-вставить, живёт в `storage.local`), `restore`
(отмена удаления), `openManager`, `openOptions`, `getSettings` / `setSettings` /
`resetSettings`, `activeTabInfo`.

### Два канала рассылки — оба обязательны

`chrome.tabs.sendMessage` доходит **только** до контент-скриптов.
`chrome.runtime.sendMessage` доходит до страниц расширения (новая вкладка, попап,
настройки), но не до контент-скриптов. Поэтому `scheduleBroadcast()` и
`broadcastSettings()` шлют в оба. Если забыть второй — панель на своей же
странице новой вкладки перестаёт видеть изменения закладок.

### Панель

`content/content.js` — один IIFE, ~1300 строк, вся панель целиком: отрисовка,
раскладка по строкам, меню, диалоги, drag & drop. Живёт в **закрытом** shadow
root внутри элемента `<dbb-bookmarks-bar>`, который вешается на
`document.documentElement` (не на `body` — тот у некоторых сайтов переписывается
целиком; на этот случай есть MutationObserver, возвращающий хост на место).

Хосту нельзя задавать `transform`, `filter`, `contain` или `will-change` — любое
из них создаёт containing block, и меню с `position: fixed` начнут
позиционироваться относительно панели, а не окна. Инлайновый стиль хоста
собирается в `hostCss()` и начинается с `all: initial !important`, чтобы правила
страницы вроде `* { margin: 0 }` до него не дотянулись.

### Фиксированные шапки сайтов

`applyPageOffset()` сдвигает страницу единственным доступным способом —
`padding-top` у `<html>`. Это двигает только поток: элемент с
`position: fixed` раскладывается относительно окна и остаётся на месте. На
YouTube `#masthead-container` прибит к `top: 0` и уходит целиком под панель
вместе с поисковой строкой.

Селектора «всё фиксированное» в CSS нет, поэтому `findFixedChrome()` ищет такие
элементы пробами `elementsFromPoint` по сетке в полосе `barHeight() + 240` от
верха окна — полоса заходит ниже самой панели, потому что вторичные строки
(лента чипов и боковое меню YouTube) прибиты не к окну, а к шапке сайта.
Найденное опускается на высоту панели.

`position: fixed` — не единственная привязка к окну. Абсолютно позиционированный
элемент без единого позиционированного предка отсчитывается от *начального*
содержащего блока, а его padding на `<html>` тоже не двигает. На этом стоят
полноэкранные приложения: у Яндекс.Карт вся оболочка — один
`div.body { position: absolute; top: 0 }`, потока под панелью нет вовсе, и под
неё уходит верх сайдбара вместе с поисковой строкой. `viewportAnchored()`
пропускает такие элементы наравне с фиксированными, отличая их по
`offsetParent === document.body`. Если же у `<body>` своё позиционирование,
абсолютные дети считаются от его padding-бокса, который уже уехал вместе с
отступом, — тогда сдвигать их нельзя, иначе отступ удвоится.

Третья привязка — `position: sticky`. Такой элемент лежит в потоке, и padding
его исправно опускает, но как только он «прилипает», он встаёт по своему порогу
`top` — то есть под панель. У Wildberries шапка высотой 116px с `top: 0`, и
верхние 61 уходили под панель. `stickyToViewport()` берёт только те липкие
элементы, чей скроллпорт — сама страница: если какой-то предок прокручивается,
порог отсчитывается от него и панель тут ни при чём.

Есть случай, который сдвигом не лечится: приложение, которое меряет
`window.innerHeight` и расставляет обвязку абсолютными координатами от окна.
Отступ опускает его целиком, и нижняя полоса уходит за край. Замерено на Google
Таблицах: панель листов при окне 945 оказывается на 970–1006, без отступа —
на 909–945. Ужать не выйдет: `body`, принудительно сжатый до
`calc(100vh - 61px)`, честно стал 884, а панель листов осталась на месте —
она считается не от коробки документа. Сканер тут ни при чём, он находит ноль
элементов.

Поэтому такие страницы распознаются — `reviewSpace()` — и вместо сдвига
уменьшается масштаб: `zoom` на `<html>` с коэффициентом
`(высота окна − высота панели) / высота окна`. Приложение по-прежнему считает,
что окно целое, и раскладывает столько же пикселей, но рисуются они в остаток
под панелью. Три детали, без которых не сходится:

- **Хост гасит масштаб обратным** (`hostCss()`): панель лежит внутри `<html>` и
  уменьшилась бы вместе со страницей.
- **Отступ задаётся с поправкой** — `pageOffset()` делит на коэффициент. Иначе
  61px внутри страницы с `zoom: 0.935` рисуются как 57 и верх приложения
  уходит под панель. Через тот же `pageOffset()` считаются и сдвиги шапок, так
  что деление покрывает и их.
- **Слишком низкое окно** (коэффициент ниже `MIN_ZOOM`) — не сжимаем, а прячем
  панель, как при автоскрытии: `barFloats()`.

Замер на Таблицах при окне 945: верх приложения ложится ровно на 61, низ панели
листов — ровно на 945, панель закладок остаётся 1920×61.

Признаков для распознавания три, и нужны все:

1. страница не прокручивается — `overflowY: hidden` у `<html>` или `<body>`,
   то есть до уехавшего вниз не добраться;
2. собственная раскладка страницы ровно в размер окна — `docFitsWindow()`,
   наш отступ при этом вычитается;
3. по нижней кромке окна идёт контент, уходящий за неё — `bottomCutOff()`,
   пробы по пяти точкам, одной разрешено не согласиться: внутренний скроллер
   свисает по замыслу.

Второе условие появилось не сразу и стоило регрессии: без него правило ловило
любую длинную страницу с открытым модальным окном — та тоже не прокручивается,
а низ у неё, разумеется, уходит за кромку. Автоскрытие включалось почти везде.
Отличает приложение-в-окно именно то, что под сгибом у него нет ничего.

Третье условие отделяет Таблицы от Яндекс.Карт: у Карт оболочка тоже во весь
экран и первые два признака совпадают, но она привязана сверху и снизу, от
сдвига корректно сжимается и ложится ровно на кромку. Замер одним предикатом:
Таблицы — 5 проб из 5 обрезаны, Карты — 0 из 5.

Признак латчится намеренно. Без отступа страница снова меряется нормально, и
повторная проверка гоняла бы панель туда-обратно; выход из режима — снятие
блокировки прокрутки (закрылось модальное окно), а не исчезновение симптома.
Ради этого наблюдатель при `spaceDenied` продолжает работать, хотя двигать
уже нечего: больше заметить снятие блокировки некому. Слушатели показа по
наведению теперь висят всегда, а не только при включённом автоскрытии, — режим
может смениться в любой момент, и без них к панели было бы не добраться.

Пять ловушек, каждая уже стоила отладки:

- **Сдвиг делается `margin-top`, а не `top`** — для всего, кроме липкого.
  Сайты сами переписывают `top` (шапки, уезжающие при прокрутке), и запись в
  то же свойство превращается в борьбу. Отступ складывается с тем, что ставит
  сайт. Липкий элемент — исключение, и не по вкусу, а по механике: отступ
  задаёт, откуда он поедет, а не где остановится, так что прилипнет он всё
  равно под панелью. Порог задаёт только `top`, и `shiftProp()` выбирает
  свойство по типу позиционирования. Что именно занято, помнит `state.prop` —
  иначе при смене позиционирования вернули бы не то свойство. Свой же
  инлайновый `top` нельзя принять за расстановку сайтом вручную, для этого
  есть `ownsTop()`.
- **`getComputedStyle().top` не отличает верхнюю привязку от нижней** — для
  позиционированного элемента возвращается *используемое* значение, и панель
  снизу с `top: auto; bottom: 0` читается как `top: 945px`. Сдвиг такой панели
  утащил бы её вверх. Настоящее `auto` отдаёт только
  `element.computedStyleMap().get('top')`.
- **Отступ не двигает фиксированные псевдоэлементы.** У `::before` с
  `position: fixed` содержащий блок — окно, а не его собственный элемент, так
  что `margin-top` уезжает вместе с шапкой, а подложка остаётся на месте. На
  Ozon весь фон прилипшей шапки нарисован именно так
  (`.uw_ia.uw_ai0::before { position: fixed; top: 0; height: 64px }`), и без
  правки от шапки оставались висящие в воздухе контролы поверх живого
  содержимого страницы. Инлайнового стиля у псевдоэлемента нет, поэтому
  смещение доезжает наследуемой переменной (`--dbb-shift-before`), а
  единственная вставленная таблица стилей превращает её в margin.
  Реальные фиксированные *дети* лечатся сами: пробы `elementsFromPoint`
  перебирают весь стек, и такой ребёнок попадает в `found` наравне с шапкой.
- **Вычисленное значение нельзя принимать за своё.** Сайты вешают переход на
  эти же свойства — у grok.com на диалоге стоит `transition: all`, — и
  `getComputedStyle()` сразу после записи отдаёт не то, что мы поставили, а
  промежуточный кадр анимации. Принятое за базу сайта, оно получает сверху
  ещё один отступ, и так каждый скан: цель растёт на высоту панели за проход
  (61, 122, 183, … — замерено), анимация её догоняет, следующий проход читает
  больше. Карточки подписки уехали на 1300px, а обратная связь
  «запись → чтение → запись» съела главный поток. Поэтому своё определяется
  по инлайновой строке, которую мы сами записали (`state.applied`), — её
  анимация не трогает, — а база сайта читается только когда нашего значения
  на элементе нет. Чужой инлайновый стиль при этом не трогаем: снять можно
  лишь то, про что есть `state`, то есть что мы точно писали сами.
- **Спуск в shadow root не завершается сам.** Shadow root спокойно отдаёт из
  `elementsFromPoint` собственный хост — так делает `<video-player>` в отзывах
  Ozon, — и скан входит в то же дерево снова и снова, пока не кончится стек.
  На странице отзывов так вело себя 20 точек проб из сетки, каждые 250 мс:
  главный поток вставал на 3.3 секунды. `checked` тут не спасает — он
  проверяется уже после спуска и к тому же общий на весь скан, а рекурсия
  зависит от точки. Поэтому у каждой пробы свой `descended`: одно вхождение в
  дерево на точку, охват прежний, петли нет. После правки скан на той же
  странице — 21–27 мс.

Скан идемпотентен: повторный проход при неизменной странице ничего не пишет.
На этом держится наблюдатель — собственная запись `margin-top` возвращается в
`MutationObserver`, и цикл затухает после одного лишнего прохода.

Работы две, и темп у них разный. **Поиск** новой шапки — дорогая сетка проб,
она ограничена `FIXED_INTERVAL`. **Удержание** уже найденного ждать не может:
сайт переключает шапку между «прилипла» и «в потоке» мгновенно, Ozon — на
каждую смену направления прокрутки, и поправка, опоздавшая на кадр, видна
глазом. Отставший отступ на вернувшемся в поток элементе роняет всю страницу
под ним на высоту панели, а заново прилипшая шапка успевает мигнуть под
панелью. Поэтому `refreshShifted()` обходит только то, что уже в `known`
(пара элементов, замеры стилей без раскладки).

Наблюдателей для этого два, и разница между ними — ровно один кадр.
`holdObserver` слушает атрибуты **только самих** удерживаемых элементов
(`observeKnown()`), поэтому срабатывает несколько раз за прокрутку, а не на
каждую мутацию страницы, и отвечать может синхронно. Это и решает: сайт
переключает класс внутри своего кадра, и `requestAnimationFrame`, заказанный
оттуда, выполнится только в следующем — это ровно один отрисованный кадр
шапки не на месте. Колбэк наблюдателя — микрозадача, он успевает в тот же
кадр, когда бы сайт ни передумал. Широкий `fixedObserver` остаётся сетью для
изменений, не трогающих атрибуты самого элемента (подмена таблицы стилей,
класс на предке), и там хватает `requestAnimationFrame`.

Собственные записи в цикл не уводят: когда всё уже на месте, пасс не пишет
ничего, и эхо от своей же записи затухает на первом проходе.

### Переполнение строк — два режима

`relayout()` ведёт себя по-разному в зависимости от настройки `wheelScroll`:

- **включена** — `#rows` становится контейнером прокрутки, ничего не прячется,
  «»» показывает то, что сейчас вне видимой области (`updateOffscreen()`);
- **выключена** — элементы за последней строкой получают класс `.overflowed`
  и скрываются, «»» показывает именно их.

При переходе во второй режим обязателен `rowsEl.scrollTop = 0`: блок с
`overflow: hidden` сохраняет прокрутку, и замеры строк врут. У `#rows` намеренно
**нет** `overscroll-behavior: contain` — иначе колесо перестаёт передаваться
странице, когда панель дошла до края.

### Меню

`placeMenu()` держит правило: выпадающий список никогда не перекрывает панель.
Меню верхнего уровня висит под **всей** панелью, а не под своей кнопкой:
по вертикали якорь — панель, по горизонтали по-прежнему кнопка. У Chrome панель
однострочная, и эти две привязки совпадают; у нас нет — меню, открытое в двух
пикселях под кнопкой первой строки, ложится поверх остальных строк. Высота
ограничивается свободным местом под панелью, список прокручивается, и только
если снизу места меньше, чем сверху, — переворачивается вверх. Подменю
переворачивается влево у правого края экрана.

С этим же связана задержка при наведении. Наведение на соседнюю кнопку при
открытом меню переключает его, как в Chrome, но на многострочной панели курсор
обязан пересечь строки между кнопкой и её же меню. Если считать это наведением,
меню закрывается раньше, чем курсор до него доедет (закрывалось: пользователь
отмечал, что попасть удаётся с пятой попытки). Поэтому движение вдоль строки
самого якоря срабатывает сразу — это осознанный жест, — а на чужой строке нужно
задержаться на `BAR_HOVER_DWELL`. Уход курсора с панели гасит отложенное
переключение: снаружи `mouseover` по панели уже не придёт, а таймер бы выстрелил.

Любое изменение закладок перерисовывает панель целиком, что вырвало бы открытое
меню из-под курсора (заметно при перетаскивании внутри меню). Поэтому `refresh()`
запоминает цепочку открытых меню и позицию прокрутки (`captureMenuState()`)
и восстанавливает её после `render()` (`restoreMenuState()`).

### Страница новой вкладки

`newtab/newtab.html` подключает тот же `content/content.js` без изменений.
Связь между ними — два глобала в изолированном мире:

- `window.__dbbThemeOverride` — `newtab.js` выставляет `'dark'`, когда включена
  настройка «тёмная страница новой вкладки» (по умолчанию **выключена**, страница
  идёт за общей темой), `applyTheme()` в контент-скрипте читает override вместо
  пользовательской темы;
- `window.__dbbRefreshTheme` — контент-скрипт публикует, `newtab.js` дёргает
  после смены настройки.

Порядок разрешения гонки: кто бы ни инициализировался первым, второй подхватит —
`newtab.js` вызывает `__dbbRefreshTheme?.()`, а `applyTheme()` читает override
каждый раз.

В инкогнито этой страницы не будет: Chrome не применяет `chrome_url_overrides`
для `newtab` в окнах инкогнито — там всегда своя страница, и контент-скрипт на
неё не попадает. Остальные переопределяемые страницы в инкогнито работают (у нас
режим `spanning` — ключа `incognito` в манифесте нет, это значение по умолчанию),
и на обычных сайтах панель в инкогнито есть. Чинить нечего: это ограничение
браузера, приходило как баг — не тратьте на него время снова.

### Настройки

`background/settings.js` — единственный источник правды (`DEFAULTS`).
Исключение одно: `newtab/newtab.js` — классический скрипт, импортировать оттуда
не может и держит свою копию `theme` и `newTabDark`. Меняя умолчание, правьте оба
места, иначе незаданный ключ на новой вкладке прочитается иначе, чем везде. Импортируется
попапом и страницей настроек напрямую, контент-скрипт получает разрешённую копию
сообщением. Новая настройка = ключ в `DEFAULTS` + поле в `options/options.html` +
имя в массиве `CHECKBOXES` / `SELECTS` / `RANGES` в `options/options.js` + строки
в обеих локалях.

## Чего делать нельзя

- **Сетевых запросов нет вообще.** Значки берутся из локального кеша браузера
  через `chrome-extension://<id>/_favicon/?pageUrl=…` (разрешение `favicon` плюс
  `_favicon/*` в `web_accessible_resources`). Это заявлено в описании магазина и
  в политике конфиденциальности — любой `fetch` наружу сломает и то и другое.
- **Никакого удалённого кода**, `eval`, `new Function`, `innerHTML`. В карточке
  магазина отмечено «удалённый код не используется».
- Разрешение `tabs` **не нужно**: `<all_urls>` и так открывает URL и заголовки
  вкладок. Оно было удалено намеренно, чтобы сократить поводы для ревью.

## Тонкости, на которых легко обжечься

- `chrome.bookmarks.move` внутри одной папки: индекс передаётся **как позиция в
  исходном списке**, Chromium сам вычитает единицу при движении вниз. Не надо
  корректировать вручную.
- Обе локали (`_locales/en`, `_locales/ru`) должны содержать одинаковый набор
  ключей; недостающий ключ не ломает сборку, а молча даёт пустую подпись.
  Интерфейс переключается по **языку браузера** (`chrome.i18n.getUILanguage()`),
  не по языку страницы и не по системе.
- Элементы с `hidden` требуют явного `[hidden] { display: none }` в `bar.css`,
  потому что `.item` задаёт `display: inline-flex` и перебивает стиль UA.
- Букмарклеты (`javascript:`) выполнить нельзя — MV3 это запрещает; расширение
  показывает об этом сообщение вместо тихого отказа.

## Соответствие нативной панели

Цвета и размеры не подбирались на глаз — они замерены попиксельно со скриншотов
встроенной панели (светлая и тёмная темы). Значения в `content/bar.css`. Меняя
палитру, сверяйтесь с нативной панелью тем же способом, а не «на вид».

Намеренные отличия перечислены в README в разделе «Насколько точно совпадает»:
кнопка «»» в крайнем правом положении, тёмный фон панели на две градации темнее
нативного, пустая страница новой вкладки. Их легко принять за баги — сверяйтесь
со списком, прежде чем «чинить».

## Отладка в Chrome

Загрузить распакованное расширение вручную: `chrome://extensions` → режим
разработчика → «Загрузить распакованное». После правок — «Обновить» на карточке
и перезагрузка страницы.

Автоматизация упирается в три ограничения, каждое из которых уже стоило времени:

1. `--load-extension` в свежих версиях Chrome игнорируется.
2. `--remote-debugging-port` не работает на профиле по умолчанию. Нужен отдельный
   `--user-data-dir`.
3. Загрузка через CDP `Extensions.loadUnpacked` требует флага
   `--enable-unsafe-extension-debugging`, **и** в `Default/Preferences` профиля
   должно стоять `extensions.ui.developer_mode: true` — иначе Chrome отключит
   расширение с причиной `DISABLE_UNSUPPORTED_DEVELOPER_EXTENSION`.

Shadow root закрытый, но DevTools его видит: `DOM.getDocument` с `pierce: true`
находит узел, `DOM.resolveNode` даёт objectId, дальше `Runtime.callFunctionOn`.
Так же проверяется drag & drop — синтетические события мыши через CDP настоящий
HTML5-перенос не запускают, приходится диспатчить `DragEvent` с собственным
`DataTransfer` прямо в shadow root.

## Публикация в магазин

`STORE.md` — статус готовности и чеклист. `store/listing.md` и
`store/fields/*.txt` — готовые тексты полей консоли разработчика.

- **Галерею расширений нельзя скриптовать расширением.** `chrome.google.com/webstore`
  и `chromewebstore.google.com` блокируют любой контент-скрипт, включая браузерную
  автоматизацию через расширение. Для работы с консолью разработчика нужен
  Playwright — на него ограничение не распространяется.
- Скриншоты и промо-плитка — **только 24-битный PNG без альфа-канала**.
- Скриншоты снимаются на синтетическом наборе закладок. Снимки с реального
  профиля в репозиторий и в магазин не попадают: они содержат личные ссылки.
  В `.gitignore` для этого есть правило на `docs/`.
